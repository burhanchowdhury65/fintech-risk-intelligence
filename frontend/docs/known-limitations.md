# Known limitations and future work

## Model (from Person B)
- MVP fraud-detection model trained on simulated transaction data. Not real financial records.
- The risk score is a relative ranking from 0 to 100, not a calibrated probability.
- Explanations are simple rule-based hints, not a formal interpretability method.
- Held-out test set (about 552,000 transactions, run once): precision 0.41, recall 0.93, F1 0.57, PR-AUC 0.88. It favours catching fraud over avoiding false alarms.
- Risk bands (low 0–39, medium 40–69, high 70–100) are provisional. No team decision has locked them.
- `transaction_type` is accepted but not used by the model.

## Frontend
- Local development uses a generated token (`DEV_JWT`) added by a server-side proxy. This is for development only and must not be deployed as is. There is no login screen.
- In live mode ARIA does not receive the dashboard result. It only knows what is said in the chat.
- ARIA's wording is generated by an AI model and may be imperfect. The risk result card comes from the risk model.
- Chat is English only (no Bangla/English toggle). History is kept in memory and cleared on reload.
- No backend status badge, no analysis history lookup, no automated test suite (checks were manual and scripted in a sandbox).
- Not verified by a person: keyboard walk with Tab, screen readers, real phones, browsers other than Chromium.
- Request timeouts are provisional (proxy 30 s for analysis, 60 s for ARIA; browser 40 s and 70 s) until ARIA latency is measured.

## Backend (reported by Person A; not observed by the frontend)
- Live ML timeout is 3 seconds. For the fixed cached demo input only, the backend then returns `source_mode: "CACHED"`; any other input gets a normal 504.
- Staging origin and the deployment authentication setup are not decided.
- Final response when both LLM providers fail is not defined.
- `score_type` and `explanation` are not in the `/analyze` response yet.
- Secret-safe log audit (tokens, API keys, transaction data) is not done.

## Counterfactual box (optional add-on)
- Shown only when the backend returns `counterfactual.found: true` for the same result. In mock mode the flagged demo carries a copy of Person B's real output for that exact input, marked "Sample data".
- Person B reports (real trained pipeline) that the flagged demo flips through the transaction amount (890 → 623, score 99 → 67, high → medium) and that 10 of 10 fresh flagged test transactions flipped through the amount. This is not yet confirmed through the full Frontend → Backend → ML path (Person A must pass the field through).
- It is an illustrative one-feature-at-a-time search. The order is amount, then hour of day, then distance from home. Tested values: amount reduced by 10, 20, 30, 50, 70, 90 and 97%; every other hour of the day; distance reduced by 50, 70, 90, 97 and 99%. "Not found" only means no flip was found in that range.
- The changed feature can differ by transaction. Do not say that lowering the amount always helps.
- The status after the change is not always low (the demo goes from high to medium).
- The backend's own `reason` text is hidden when it only repeats the two values already shown in the sentence.
- The slider that re-analyzes live was not built (the roadmap marks it optional and risky).

## Future work
Real login, backend status badge, analysis history, Bangla/English toggle, calibrated probability, a richer explanation method, automated end-to-end tests, the optional Sector Node.
